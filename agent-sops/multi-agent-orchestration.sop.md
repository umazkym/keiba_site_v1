# Multi-Agent Orchestration

## Overview

このSOPは、指揮役（利用者と話す会話）が、作業員（Agent 道具で出す別の会話）と Codex に仕事を分けて、並べて進めるときの手順です。観点が2つ以上ある調査、直すファイルが重ならない実装が2つ以上あるとき、本人でない目の点検が要るときに使います。1人で済む小さな直しには使いません。仕事の分け方、依頼文と報告の型、指揮役の点検、作業員・指揮役・利用者の気づきを SOP・スキル・記憶に返す流れを扱います。

ランサーズのリポジトリの「並べて進める」（役割の表・状況.md・報告の型・過剰に直さない決まり）を、UMA-FREE に合わせた物です。作業員に渡す決まりのひな形は `agent-sops/templates/`、気づきの記録は `agent-sops/feedback-log.md` にあります。

## Parameters

- **user_request** (required): 利用者の依頼。言い換えずに原文のまま持つ（依頼文にもそのまま入れる）。
- **stage** (optional, default: "auto"): `調査`、`実装`、`点検` のどれか。
- **work_folder** (optional, default: `.local/analysis/<今日の日付>/`): 作業員のフォルダと、決まりの写しを置く場所。git の対象外。
- **max_parallel** (optional, default: 3): 同時に動かす作業員の数。
- **single_tools** (optional): 1つしかない道具と、その担当（専用 Chrome・開発用サーバー・フロントのビルドなど）。

Constraints for parameter acquisition:

- 日付は `date` で取る。覚えで書かない（要約をまたぐと日付がずれるため）。
- 大きな直しを並べて行うことを利用者が頼んでいないときは、始める前に一言確かめる。AGENTS.md の 9 章が、並行の大きな修正に利用者の許可を求めているため。
- 質問と素材のお願いは、作業員を出す前に1回にまとめる。出した後に前提が変わると、全員をやり直すことになるため。

## Steps

### 1. 使うかどうかを決める

作業員を出すと、依頼文を書く手間と、報告を点検する手間が増えます。分ける得が手間を上回るときだけ使います。

**Constraints:**

- 使う：観点が2つ以上ある調査／直すファイルが重ならない実装が2つ以上／書いた本人でない目で見る点検。
- 使わない：1〜2ファイルの小さな直し、場所の分かっている調べもの、順番にしか進められない仕事。依頼文を書くより自分で直す方が早く、取りこぼしも少ないため。
- 大人数で一斉に進める道具（Workflow など）は、利用者が頼んだときだけ使う。使用量が一度に大きく出るため。
- 同じプロジェクトでファイルを直す会話は、指揮役の会話1つにする。始める前に `.claude/handoff.md` で、ほかの会話が直していないかを確かめる。2つの会話が同じ作業フォルダを直すと、互いの直しを上書きするため。

### 2. 役割を決める

| 役割 | すること | しないこと |
| --- | --- | --- |
| 指揮役 | 利用者と話す。仕事を分け、依頼文を書く。報告を点検する。共有の物（SOP・記憶・引き継ぎメモ・`repository:map`）を直す。コミットの単位を決める | 作業員の担当ファイルを、作業員が動いている間に直す。大きなファイルを丸ごと読む |
| 調査の作業員 | 1つの観点を調べ、自分のフォルダに `分析.md`・`施策の案.md`・`状況.md` を書く | コードを直す。自分のフォルダの外に書く |
| 実装の作業員 | 依頼文に書かれたファイルだけを直し、テストを動かし、報告する | 書かれていないファイルを直す。git の状態を変える |
| Codex | 指揮役の指示どおりの画像生成と雑務（調べもの・変換・テスト・点検）。動かし方は `~/.claude/memory/codex-claude-workflow.md` | デザインの判断、お金・削除・公開・送信・push |

**Constraints:**

- 作業員には、git の add・commit・push・stash・reset・checkout をさせない。ほかの作業員の直しが同じ作業フォルダにあり、まとめて戻す操作は全員の直しを消すため。
- 作業員には、本番へのアクセス、Workflow の起動、デプロイ、DB への接続、クラウドや広告の設定変更、お金のかかる操作をさせない。戻せない操作の判断は、利用者と話せる指揮役だけができるため。
- 作業員に作業員を出させない。誰が何を直しているかを指揮役が追えなくなるため。
- 共有の物を直す作業員が要るときは、担当を1人だけ決めて依頼文に書く（例：2026-10-02 は `agent-sops/` の担当が1人）。

### 3. 仕事を分ける

**Constraints:**

- 調査は観点ごと、実装は「直してよいファイル」ごとに分ける。同じファイルを2人に渡さない。あとから差分を分けられなくなるため。
- 1人に渡すのは、1つの観点・1つの段まで。2026-10-02 は範囲が広すぎて、指揮役と作業員3人が自動要約の空回り（Autocompact is thrashing）で止まり、約7時間でコードの直しが0だった。
- 同時に動かすのは、画像を多く読む作業員なら3人まで（2026-09-25、5人が3往復して使用量の上限に達した）。範囲が狭く、画像を読まず、1つの段で終わる作業員は7人まで実例がある（2026-10-02、7人とも止まらず、やり直しなし。1人あたり約6万〜11万トークン・10〜45分）。それを超えたときは、結果を `agent-sops/feedback-log.md` に書く。
- 1つしかない道具（専用 Chrome のポート 9344・開発用サーバー・`next build`）は、担当を1人だけ決めて依頼文に「担当」と書く。同時に使うと、ポートや `.next` がぶつかるため。
- 全体にかかる命令（`npm run repository:map`・`npm run agent-sops:skills`）は、最後に1回だけ動かす。途中で動かすと、ほかの作業員の途中の状態を写すため。
- 同じファイルで施策を分けてコミットしたいときは、段ごとにファイルの写しを残させる（`<作業員のフォルダ>/step0/`＝直す前、`step1/`＝1つ目の後）。
- 前の結果を使う仕事は並べない。先の作業員の報告を点検してから、次を出す。

### 4. 作業員の決まりと依頼文を用意する

決まりは、ひな形（`agent-sops/templates/worker-rules-research.md`・`worker-rules-implementation.md`）を `<work_folder>/_作業員の決まり.md`・`_実装の作業員の決まり.md` に写し、`<…>` を埋めて使います。依頼文は次の型で書きます。

```text
あなたは UMA-FREE の<調査｜実装>の作業員です。担当：<一言>
## 利用者の依頼（原文）
## 最初に読む物（この順で。行の範囲つき）
## 分かっていること（確かめた事・除いた仮説・前に止まった理由）
## やること／作る物
## 直してよいファイル（調査なら：書いてよい場所）
## 1つしかない道具（担当か、使わないか）
## 確かめ方（動かす命令）
## 終わり方（状況.md と、決まりの報告の形。行数の上限）
```

**Constraints:**

- 利用者の依頼は原文のまま入れる。言い換えると、要約のたびに細かい条件が抜けるため。
- 「最初に読む物」は、順番と行の範囲を書く。100KB を超える JSON・ログや 3,000 行を超えるコードは、指揮役が小さな資料にまとめてから渡す。丸ごと読むと、作業員が始める前に文脈が埋まるため。
- 分野の SOP は指揮役が選び、1〜2本を名前で渡す。全部を読ませない（`task-intake-and-sop-routing.sop.md` の 2）。
- 「分かっていること」に、除いた仮説を書く。書かないと、作業員が同じ所を調べ直すため。
- 指揮役の見立ては「見立て」と書いて渡す。確かめた事として渡すと、作業員がそのまま確かめた事として返すため。

### 5. 出して、待つ

**Constraints:**

- 独立した作業員は、1回の発言でまとめて出す（同時に動く）。
- 判断の要る仕事は Opus、決まった手順の雑務は軽いモデルか Codex に回す。使用量を抑えるため。
- 待つ間に、作業員の担当ファイルを直さない。届いていない報告を先回りして書かない。
- 止まった作業員を再開させない。同じ依頼をそのまま出し直さない。自分のフォルダに残った成果物を確かめ、範囲を狭めた依頼を新しく出す。同じ範囲では同じ所で止まるため。

### 6. 報告を受けて点検する

報告は、作業員が「した」と言っている事の一覧です。指揮役が差分とテストを自分で確かめてから、利用者に伝えます。

**Constraints:**

- `git status --short` で、依頼文に無いファイルが変わっていないかを見る。変わっていたら、誰の直しかを確かめてから扱う。
- `git diff -- <ファイル>` を読む。大きな差分は `--stat` で大きさを見てから、要る所だけ読む。
- テストを自分でも動かし、合格と失敗の数を報告と比べる。期待値を変えたテストは、1件ずつ理由を読む。
- 画面の変更は、手元のビルドでスマホ幅と PC 幅を1画面ずつ撮る。本番は開かない（`.claude/CLAUDE.md` のつまずきポイント）。
- 「未確認」は、自分で確かめるか、未確認のまま利用者に伝える。確かめずに「できた」に書き換えない。
- 調査の報告にある「コードの事実」（何がどこに有る・無い）は、施策にする前に指揮役がその行を読んで確かめる。2026-10-02 は、画面だけを見た作業員の読み違いが2件あった（サイトマップに入っているページを「入っていない」、リンクを「押せない文字」）。
- 「利用者に聞くこと」は全員の分をまとめ、1回で聞く。作業ハブが止まっている間は `.claude/handoff.md` に書く。

### 7. コミットの単位に分ける

**Constraints:**

- 1つの施策を1つの単位にする。あとで効果を比べたり、1つだけ戻したりできるようにするため。
- 同じファイルに施策が2つ入っているときは、3 の写しを順に当てて区切る。
- commit と push は、AGENTS.md の既定では利用者が行う。利用者がその会話で commit を頼んだときだけ、指揮役が commit する。push と公開は、計画を示して許可をもらってから。作業員はどちらもしない。
- ページや自動処理を足した・消したときは、`npm run repository:map` と `npm run repository:check` を動かす。2026-09-26 に見落として、CI が3回失敗した。

### 8. 気づきを記録し、SOP・スキル・記憶に返す

気づきの入口は3つです。(a) 作業員の報告の「覚えること」「直してほしい道具・手順」、(b) 指揮役が点検で気づいた事、(c) 利用者の指摘。どれも、まず `agent-sops/feedback-log.md` に1件ずつ足します。置き場所を1つにするのは、次の会話が1か所を読めば済むようにするためです。

| 気づきの種類 | 返す先 |
| --- | --- |
| 1回だけ出た事 | 記録だけ（2回目が出たら直す） |
| 2回出た事／止まった・壊した・やり直した事／利用者が指摘した事 | SOP かひな形を直す |
| 作業員が守る事 | `agent-sops/templates/` のひな形 |
| 指揮役の進め方 | この SOP |
| 分野の事（記事・広告・計測・ビルドなど） | その分野の SOP |
| 道具のつまずき | 道具を直す。直せなければ、ひな形の「道具のつまずき」 |
| 利用者の好み・決めたこと | 記憶（このプロジェクトの事はプロジェクトの記憶、共通の事は `~/.claude/memory/`） |
| ほかのプロジェクトでも効く使い方 | `~/.claude/memory/claude-code-playbook.md` |

**Constraints:**

- 報告を受けたら、その場で記録に足す。あとでまとめると、要約で抜けるため。
- 利用者の指摘は、その場で返す先を決めて直す。直す前に、指摘の対象を数える（1か所の話か、全体の話か）。「消す」の前に「変える」を考える。褒められた部分は残す。1つの指摘で全体を作り変えると、良かった所まで失うため。
- SOP とひな形の直しは、段の区切りにまとめて行い、`npm run agent-sops:validate` と `npm run agent-sops:skills` を通す。`.claude/skills/` は生成物なので、手で直さない。
- 足すだけにしない。古い文を直すか、削る。決まりが増えすぎると、矛盾して質が下がるため。
- 作業員には、記憶・SOP・引き継ぎメモを書かせない（担当と決めた1人を除く）。作業員は報告に書き、指揮役が返す。
- 記録に、鍵・トークンの値、メールアドレス、支払いの個人情報を入れない。`agent-sops/` は git に入るため。
- 「記録だけ」のままの項目は、月に1回か、次にこの SOP を使う前に見直す。反映が済んで古くなった項目は消してよい（git の履歴に残る）。
- 2つのひな形には同じ章（してはいけないこと・文脈をあふれさせない・道具のつまずき）がある。片方を直したら、もう片方も合わせる。

### 9. ほかの SOP・スキルと組み合わせる

**Constraints:**

- 入口は `task-intake-and-sop-routing.sop.md`。分野の SOP を選んでから、この SOP で分ける。
- 分野の SOP は、作業員の「最初に読む物」に名前で渡す。検証は、その SOP の決まりに従う（例：画面は `frontend-build-release-verification.sop.md`、記事は `article-quality-gate.sop.md`）。
- 始める前の合意はスキル kickoff、画面の確認はスキル look-check、本人でない目の点検はスキル second-look を使う。
- SOP を直すときは `sop-authoring.sop.md` に従う。

## Troubleshooting

### 作業員が「Autocompact is thrashing」で止まった

再開させません。作業員のフォルダに残った成果物（`状況.md`・`_tmp/`）を確かめ、できている所を除いて、範囲を狭めた依頼を新しく出します。読む物は、指揮役が小さな資料にしてから渡します。

### 依頼文に無いファイルが変わっていた

`git status --short` と `git diff -- <ファイル>` で中身を見て、どの作業員の直しかを報告と突き合わせます。まとめて戻す操作（`git checkout .`・`git stash`）は、ほかの作業員の直しも消すので使いません。

### 2人の直しが同じファイルに入った

分け方の誤りです。差分を読んで施策ごとに区切り、区切れないときは片方を指揮役が当て直します。`agent-sops/feedback-log.md` に書き、次は 3 の「直してよいファイル」で分けます。

### テストの数が報告と合わない

指揮役が動かした結果を正とします。ほかの作業員の直しが後から入った可能性があるので、失敗したテストがどのファイルの直しに関係するかを先に見ます。
