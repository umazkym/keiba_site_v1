### 2.2.3 レンダリング戦略

#### Static Site Generation (SSG)
- **対象**: 固定ページ(About, Privacy, Terms, etc.)
- **メリット**: 最高速のページロード
- **タイミング**: ビルド時

#### Server-Side Rendering (SSR)
- **対象**: 検索ページ、動的クエリを含むページ
- **メリット**: 最新データを保証
- **タイミング**: リクエスト時

#### Incremental Static Regeneration (ISR)
- **対象**: レースページ、記事ページ
- **再生成間隔**: 5分 (300秒)
- **メリット**: 静的ページのパフォーマンス + データの鮮度
- **実装例**:
```typescript
export const revalidate = 300; // 5分
```

#### Static Params Generation
- **対象**: レースページ (`/races/[date]`)
- **生成範囲**: 過去30日 〜 未来14日
- **実装**:
```typescript
export async function generateStaticParams() {
  const dates = [];
  for (let i = -30; i <= 14; i++) {
    dates.push({
      date: format(addDays(new Date(), i), 'yyyy-MM-dd')
    });
  }
  return dates;
}
```

### 2.3.3 レイヤー構成

#### 1. API Layer (FastAPI)
- **役割**: HTTPリクエストの受付とレスポンス返却
- **責務**: ルーティング、リクエスト検証、エラーハンドリング
- **ファイル**: `api/v1/endpoints/predictions.py`

#### 2. Business Logic Layer (CRUD)
- **役割**: ビジネスロジックの実装
- **責務**: データの加工、集計、フィルタリング
- **ファイル**: `crud/*.py`

#### 3. Data Access Layer (SQLAlchemy Models)
- **役割**: データベースとのやり取り
- **責務**: クエリ発行、トランザクション管理
- **ファイル**: `database/models/*.py`

#### 4. Schema Layer (Pydantic)
- **役割**: データ検証とシリアライゼーション
- **責務**: 型チェック、JSON変換
- **ファイル**: `schemas/*.py`

#### 5. Data Processing Layer (Scripts)
- **役割**: 外部データの取得と処理
- **責務**: スクレイピング、解析、予測生成
- **ファイル**: `scripts/*.py`

## 2.4 データベースアーキテクチャ

### 2.4.1 RDBMS選定

**本番環境**: PostgreSQL
- **理由**:
  - トランザクションの信頼性
  - JSON型サポート(matchupデータ、corner_positions)
  - インデックス機能の充実
  - Renderでのマネージドサービス提供

**開発環境**: SQLite
- **理由**: セットアップ不要、軽量、ポータビリティ

### 2.4.2 接続管理

```python
# database/session.py
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
import os

# 環境に応じた切り替え
DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./keiba.db")

# PostgreSQLの場合、psycopg2に変換
if DATABASE_URL.startswith("postgres://"):
    DATABASE_URL = DATABASE_URL.replace("postgres://", "postgresql://", 1)

# 本番環境では接続プール制限
if "postgresql" in DATABASE_URL:
    engine = create_engine(
        DATABASE_URL,
        pool_size=3,          # 最大3接続
        max_overflow=0,       # オーバーフロー禁止
        pool_pre_ping=True    # 接続チェック
    )
else:
    engine = create_engine(DATABASE_URL)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
```

### 2.4.3 テーブル設計の原則

1. **正規化**: 馬、騎手、調教師は独立したテーブル

3. **複合ユニーク制約**: 重複データの防止
4. **JSON型の活用**: 可変長データ(corner_positions, matchup_data)
5. **インデックス**: 頻繁に検索されるカラムに付与

logger = logging.getLogger(__name__)

logger.info("Starting scraper...")
logger.warning("Rate limit approaching...")
logger.error("Failed to fetch data", exc_info=True)

## 2.11 アーキテクチャ上の設計原則

### 2.11.1 SOLID原則の適用

- **Single Responsibility**: 各モジュールは単一の責務
- **Open/Closed**: 拡張に開いて修正に閉じる
- **Liskov Substitution**: サブクラスは基底クラスと置き換え可能
- **Interface Segregation**: 必要なインターフェースのみ実装
- **Dependency Inversion**: 抽象に依存、具象に依存しない

### 2.11.2 DRY (Don't Repeat Yourself)

- 共通処理は関数化
- ユーティリティモジュールの活用
- コンポーネントの再利用

### 2.11.3 関心の分離 (Separation of Concerns)

- **プレゼンテーション層**: React Components
- **ビジネスロジック層**: CRUD + Predictor
- **データアクセス層**: SQLAlchemy Models
- **データソース層**: Database
