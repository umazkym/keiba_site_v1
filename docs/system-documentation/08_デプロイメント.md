# 08. デプロイメント

> **2026-08-04移行注記（2026-08-27更新）**: Vercel Hobbyは使用量超過でpauseされ、フロントエンドはCloud Run + Cloudflareへ**移行済み**です。切替手順、証明書、DNS、キャッシュ、WAF、ロールバックの正は`docs/cloud_run_cloudflare_migration_20260804.md`とします。本章内に残るVercel記述（§8.4）は履歴・ロールバック調査用の参照であり、現行構成ではありません。

## 8.1 デプロイメント概要

### 8.1.1 ホスティング環境

| コンポーネント | プラットフォーム | プラン | 備考 |
|--------------|----------------|-------|------|
| フロントエンド | Cloud Run `keiba-frontend-v1` + Cloudflare | 従量課金 + Free | Next.js standalone。Vercelは廃止（§8.4は履歴） |
| バックエンドAPI | Google Cloud Run | 無料枠 | FastAPI (Python) |
| データベース | GCE VM (e2-micro) | 永久無料枠 | PostgreSQL 15 自前構築 |
| Cronジョブ | GitHub Actions | 無料 | データ収集・予測・SNS |

### 8.1.2 デプロイフロー

```text
利用者 → Cloudflare → Cloud Run frontend → Cloud Run FastAPI → GCE PostgreSQL
                       ↑ 手動GitHub Actions      ↑ Direct VPC / IAP保守
```

フロントエンドのproduction deployは`.github/workflows/deploy-frontend-cloud-run.yml`をユーザーが手動実行します。GitHub pushだけでは自動デプロイしません。

## 8.2 Google Cloud Run デプロイ設定

### 8.2.1 サービス情報

| 項目 | 値 |
|:---|:---|
| サービス名 | `keiba-site-v1` |
| リージョン | `us-west1` |
| プロジェクト | `keiba-api-project` |
| VPCネットワーク | `default` |
| VPC Egress | `private-ranges-only` |

### 8.2.2 環境変数設定

**Cloud Runサービスで設定**:

```bash
# データベース (GCE VM 内部IP経由)
DATABASE_URL=postgresql://keiba_user:***@10.138.0.2:5432/keiba_db

# その他
TZ=Asia/Tokyo
```

**楽天API / アフィリエイト連携**:

楽天Web Serviceの実キーは、リポジトリへ直書きせず、GCE VM、Cloud Run、GitHub ActionsのSecret/環境変数として設定します。

```bash
RAKUTEN_API_APPLICATION_URL=https://uma-free.com
RAKUTEN_API_APPLICATION_ID=xxx
RAKUTEN_API_ACCESS_KEY=xxx
RAKUTEN_AFFILIATE_ID=xxx
```

商品検索APIを固定IP制限つきで利用する場合は、GCE VM `keiba-db` の外部IP `34.182.6.97` を楽天側の許可IPに登録し、GCE上の同期バッチから楽天APIを呼び出します。Cloud Runから直接楽天APIを呼ぶ場合は、Cloud NATによる静的アウトバウンドIP構成が必要です。

Cloud Run `keiba-site-v1` から楽天APIを呼び出す場合は、Cloud NATの固定送信元IP `35.252.200.91` を楽天側の許可IPに登録します。Cloud Runの受信用URLではなく、外部APIへ出ていく送信元IPが許可対象です。

フロントエンド側の楽天市場リンクは通常の商品URLを保持し、ブラウザ表示時にCloud Runの `/api/v1/affiliate/rakuten/resolve` を呼び出して楽天APIの `affiliateUrl` に差し替えます。これにより、楽天APIキーやAccess Keyをブラウザへ出さずに、楽天アフィリエイトURLを利用できます。

### 8.2.3 デプロイ手順

1. **自動デプロイ**:
   - **フロントエンド (`keiba-frontend-v1`)**: `.github/workflows/deploy-frontend-cloud-run.yml` が担当。`main` への push で動くのは Repository Variable `CLOUD_RUN_FRONTEND_AUTO_DEPLOY_ENABLED` が `true` のときだけです。**2026-08-27 時点の値は `true`** で、`frontend/**` の変更を含む push、および記事パイプライン（1日3回）とGSC週次からの呼び出しでデプロイが走ります。イメージは `keiba-containers` へ commit SHA タグで push されます（最大90 push/月程度）。
   - **バックエンドAPI (`keiba-site-v1`)**: **自動デプロイはありません。** リポジトリに `cloudbuild.yaml` は存在せず、Cloud Build のトリガーによる自動デプロイも確認できていません（2026-08-27 時点）。下記の手動デプロイのみです。

2. **手動デプロイ** (必要な場合):
   ```bash
   gcloud run deploy keiba-site-v1 \
     --project=keiba-api-project \
     --region=us-west1 \
     --source=.
   ```

   > **注意（2026-08-27 確認）**: `--source` ビルドの成果物は Artifact Registry の
   > `cloud-run-source-deploy/keiba_site_v1/keiba-site-v1` に commit SHA タグで格納され、
   > Cloud Run 側で command/args は指定していない（イメージのCMDをそのまま使う）。
   > ただし `backend/Dockerfile` の CMD は `python run_pipeline.py` であり、
   > HTTPを返している実サービスと整合しない。**どのビルド経路が実際に使われているかは未確定。**
   > また `backend/Dockerfile.api`（軽量・Chrome無し）はリポジトリ内のどこからも参照されていない。
   > API イメージをどちらに寄せるかは未決の課題（`12_コスト最適化アーキテクチャ.md` §11.8）。

3. **ログ確認**:
   ```bash
   gcloud run services logs read keiba-site-v1 \
     --project=keiba-api-project \
     --region=us-west1 \
     --limit=20
   ```

### 8.2.4 Cloud Run ↔ GCE VPC接続

Cloud RunからGCE VMのPostgreSQLへは**VPC内部IP (10.138.0.2)** で通信します。

```bash
# VPC Egress設定の確認
gcloud run services describe keiba-site-v1 \
  --project=keiba-api-project \
  --region=us-west1 \
  --format="value(spec.template.metadata.annotations['run.googleapis.com/vpc-access-egress'])"
```

## 8.3 GCE VM (PostgreSQL) 管理

### 8.3.1 VM情報

| 項目 | 値 |
|:---|:---|
| インスタンス名 | `keiba-db` |
| マシンタイプ | `e2-micro` (永久無料枠) |
| ゾーン | `us-west1-b` |
| 内部IP | `10.138.0.2` |
| 外部IP | `34.182.6.97` (静的) |
| OS | Debian |
| PostgreSQL | 15 |

### 8.3.2 SSH接続

```bash
gcloud compute ssh keiba-db --zone=us-west1-b --project=keiba-api-project
```

### 8.3.3 PostgreSQL管理コマンド

```bash
# SSH接続後
sudo -u postgres psql keiba_db

# テーブル一覧
\dt

# レース数確認
SELECT COUNT(*) FROM races;

# PostgreSQLサービス管理
sudo systemctl status postgresql
sudo systemctl restart postgresql
```

### 8.3.4 ファイアウォール設定

```bash
# 現在のルール確認
gcloud compute firewall-rules list --project=keiba-api-project

# 公開allow-postgresが無効で、IAP専用ルールだけが有効なことを確認
gcloud compute firewall-rules describe allow-iap-postgres-keiba-db --project=keiba-api-project
```

### 8.3.5 PostgreSQL設定ファイル

```bash
# postgresql.conf の主要設定
shared_buffers = 256MB
max_connections = 50
listen_addresses = '*'

# pg_hba.conf の主要設定
# Cloud RunのVPCサブネット
host    keiba_db    keiba_user    10.0.0.0/8        md5
# GitHub Actions・保守はIAP TCPトンネルだけを使う。
# 0.0.0.0/0を追加せず、実際のIAP接続元だけを許可する。
```

## 8.4 Vercel旧デプロイ設定（移行参照のみ）

Vercelのプランはアップグレードしない。以下は環境値移行とロールバック調査の参照であり、新規production deploy先には使わない。Cloud Run側では同名の`NEXT_PUBLIC_*`をGitHub Repository Variablesからbuild時に渡す。

### 8.4.1 プロジェクト設定

**vercel.json** (オプション):
```json
{
  "buildCommand": "cd frontend && npm run build",
  "outputDirectory": "frontend/.next",
  "devCommand": "cd frontend && npm run dev",
  "installCommand": "cd frontend && npm install",
  "framework": "nextjs",
  "rewrites": [
    {
      "source": "/api/:path*",
      "destination": "https://keiba-site-v1-761440273070.us-west1.run.app/api/:path*"
    }
  ]
}
```

### 8.4.2 環境変数

**Vercelダッシュボードで設定**:

```bash
# API URL
NEXT_PUBLIC_API_URL=https://keiba-site-v1-761440273070.us-west1.run.app

# Google Analytics
NEXT_PUBLIC_GA_ID=G-XXXXXXXXXX
NEXT_PUBLIC_ANALYTICS_RELEASE_ID=2026-08-01-ga-route-v2

# Google AdSense
NEXT_PUBLIC_ADSENSE_CLIENT_ID=ca-pub-XXXXXXXXXXXXXXXX

# モバイルレース広告試作（開始ゲート合格まではlegacy固定）
NEXT_PUBLIC_RACE_REVENUE_EXPERIMENT_MODE=legacy
NEXT_PUBLIC_RACE_ENGAGED_AD_SLOT=7550236816
```

`NEXT_PUBLIC_RACE_REVENUE_EXPERIMENT_MODE=split`は、高速ゲート（3完全日・主要欠損と`Unassigned`が各2%未満・合計500セッション以上）または標準ゲート（7完全日・各5%未満）を通過し、D+7・D+14の判断リマインドを登録した後だけ反映します。即時復元値は`legacy`です。

### 8.4.3 デプロイ手順

1. **自動デプロイ**: GitHubのmainブランチへのpushで自動デプロイ
2. **ロールバック**: Vercel Dashboard → Deployments → 前のデプロイを選択 → Promote to Production

## 8.6 バックアップ戦略

### 8.6.1 データベースバックアップ

**手動バックアップ**:
```bash
# GCE VMにSSH接続後
sudo -u postgres pg_dump keiba_db > backup_$(date +%Y%m%d).sql

# ローカルにダウンロード
gcloud compute scp keiba-db:~/backup_YYYYMMDD.sql . \
  --zone=us-west1-b --project=keiba-api-project
```

**将来の自動化** (推奨):
```bash
# GCE VM上にcronジョブを設定
0 3 * * 0 sudo -u postgres pg_dump keiba_db | gzip > /var/backups/keiba_db_$(date +\%Y\%m\%d).sql.gz
# 古いバックアップを自動削除 (30日以上)
0 4 * * 0 find /var/backups/ -name "keiba_db_*.sql.gz" -mtime +30 -delete
```

### 8.6.2 コードバックアップ

**GitHub**: 自動的にバージョン管理

**タグ付け**:
```bash
git tag -a v1.0.0 -m "Production release 1.0.0"
```

## 8.9 コスト

| サービス | プラン | 月額 |
|---------|-------|------|
| Cloudflare | Free | 基本$0、plan内制限あり |
| Cloud Run frontend / API | 従量課金・無料枠あり | 実使用量、egress、請求先全体で変動 |
| Artifact Registry | 従量課金・無料枠あり | image保存量で変動 |
| GCE VM (e2-micro) | 無料枠対象構成 | disk・network等で変動し得る |
| GitHub Actions | 利用枠内 | 実行時間で変動し得る |

固定の「合計$0」は保証しない。Cloud Run billable instance time、requests、egress、Artifact Registry保存量、請求アラートを月次で確認する。
