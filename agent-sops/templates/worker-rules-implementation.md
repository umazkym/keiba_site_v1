# 実装の作業員の決まり（UMA-FREE・<作業の名前>・<日付>）

> ひな形（原本：`agent-sops/templates/worker-rules-implementation.md`）。指揮役が `<作業フォルダ>/_実装の作業員の決まり.md` に写し、`<…>` を埋め、この囲みを消して使う。決まりそのものを直したいときは、写しではなく原本を直す（`agent-sops/multi-agent-orchestration.sop.md` の 8）。

指揮役（利用者と話す会話）が、直すファイルごとに作業員を出す。作業員は **1つの直しの1つの段** を受け持ち、最後まで自分の判断で進め、短く報告して終わる。ほかの作業員を待たない。ここは **コードを直す段** の決まり。

リポジトリ：`<リポジトリの場所>`（Bash では `<リポジトリの場所・Bash の形>`）
設計の元になる資料（**行の範囲を指定して読む。丸ごと読まない**）：`<指揮役がまとめた資料のパス>`

## 1. 直してよいファイル
- **依頼文に書かれたファイルだけ**。ほかの作業員が同時に別のファイルを直している。書かれていないファイルを直したくなったら、直さずに報告の「直してほしい所」に書く。
- 一時のファイル・見本・差分の写しは、依頼文で渡された自分のフォルダ（`<作業フォルダ>/<名前>/`）に置く。
- `agent-sops/`・`.claude/`・`AGENTS.md`・`DESIGN.md`・記憶・引き継ぎメモは、依頼文で渡されたときだけ直す。

## 2. してはいけないこと（どれも理由がある。回り道もしない）
- **git の add・commit・push・stash・reset・checkout（ファイルを戻す操作）をしない**。コミットの区切りは指揮役がまとめて決める。ほかの作業員の直しが同じ作業フォルダにあるので、`git add -A`・`git stash`・`git checkout .` は事故になる。差分を見るのは `git diff -- <自分のファイル>` だけ。
- **本番（uma-free.com）へアクセスしない**（curl・WebFetch・ブラウザ・スクリプトのどれでも）。2026-09 に自宅の回線が締め出された。
- GitHub の Workflow を起動しない（`gh workflow run` をしない）。デプロイしない。DB へつながない。楽天競馬のリンクを押さない。
- クラウド・IAM・Cloudflare・AdSense・GA4・Search Console の設定を変えない。お金のかかる操作をしない。
- **数字・名前・日付を作らない**。確かめていないことは「未確認」と書く。
- 鍵・トークンの値、メールアドレス、支払いの個人情報を表示・記録しない。
- 作業員をさらに出さない（Agent 道具を使わない）。誰が何を直しているかを、指揮役が追えなくなる。
- 開発用サーバー・フロントのビルド（`next build`／`next dev`／`next start`）と専用 Chrome（ポート 9344）は、依頼文で「担当」と書かれた作業員だけが使う。同時に使うと、ポートや `.next` がぶつかる。
- 文体：強い表現（「投資」「必勝」「絶対」「圧倒的」「最強」「消去対象」など）を、コード中の文言にも入れない（AGENTS.md）。

## 3. 文脈をあふれさせない（2026-10-02、指揮役も作業員3人もここで止まった）
- **大きなファイルを Read で丸ごと読まない**。3,000行を超えるコードは、Grep（Bash の `grep -n`）で場所を見つけ、Read は `offset`・`limit` で 200行以内ずつ。
- JSON・TSV・ログ（100KB を超える物）は Read しない。小さな Python スクリプト（**Write 道具で作る**。Bash の heredoc で作らない）で要る所だけ取り出し、出力は数十行までにする。出力が長くなる命令は `| head -60` か、ファイルへ書いて行数だけ見る。
- pytest は `-q` と `--tb=short`、失敗の表示は `| tail -40`。
- 画像（Read）は、要る物を数枚だけ。
- 成果物（コードの直し・状況.md）は **早めに書き出す**。追記は小分けにする。考えをためてから一度に書かない（書く前に止まると、何も残らない）。
- 1つの段で終わる。範囲が広がったら、広げずに報告へ書く。

## 4. 道具のつまずき
- Bash は毎回 `cd <リポジトリの場所・Bash の形> &&` で始める（作業ディレクトリが動く）。
- Python の出力は `sys.stdout.reconfigure(encoding="utf-8")`。
- 日本語のパスは、Bash では文字化けし、Grep 道具でも効かないことがある → Glob・Read 道具（絶対パス）か PowerShell で扱う。
- リポジトリ全体への `grep -r` は時間切れになる → `git grep -n "<語>" -- <フォルダ>`。Grep 道具の glob は、波かっこ（`*.{ts,tsx}`）と隠しフォルダで当たらないことがある。
- pytest はリポジトリの一番上から：`python -m pytest backend/tests/<ファイル> -q --tb=short`。
- npm の命令は置き場所が2つある。記事・画面の検査（`article:test-flow`・`design:audit` など）は `frontend/`、`repository:*`・`agent-sops:*` はリポジトリの一番上。
- gh は `export GH_TOKEN=$(gh auth token --user <このリポジトリの GitHub アカウント>)` のあと（読むだけ：`gh run list`・`gh run view`）。
- コードは、まわりの書き方（名前・コメントの量・日本語のコメント）に合わせる。省略（`...`）を残さない。
- <この作業だけの道具のつまずきがあれば、指揮役が足す>

## 5. 確かめてから「できた」と言う
- 直したら、関係するテストを自分で動かす。合格の数と失敗の数を、そのまま報告に書く。動かせなかったら「未確認」と書く。
- 既存のテストを直すときは、何を・なぜ直したかを1件ずつ報告に書く（黙って期待値を変えない）。
- 同じファイルの中で施策を分けるよう頼まれたときは、段ごとにファイルの写しを自分のフォルダに残す（`step0/`＝直す前、`step1/`＝1つ目の施策の後、…）。指揮役が施策ごとに区切るのに使う。

## 6. 状況.md（自分のフォルダに。30行まで。最初に書き、進むたびに直す）
```
# 状況（<担当>）
段：<調査｜実装｜点検>（<日時。date で取る>）
誰の番：<利用者｜指揮役｜作業員>
次の一手：
## できている物
## 自分で決めたこと
## 覚えること（利用者の好み・学び・次も使える調べ方）
## 利用者に聞くこと
## 経緯（新しい順・1行ずつ）
```

## 7. 報告（最後の返事。指揮役がそのまま読む。25行以内）
```
段：実装 → 点検（指揮役の番）
直したファイル：<パス（何を直したか一言）>
施策ごとの差分の写し：<依頼文で求められたとき。パス>
テスト：<命令と結果（合格 N・失敗 N）>
確かめたこと（証拠）：
利用者に聞くこと：<無ければ なし>
自分で決めたこと：
未確認：
直してほしい所（自分の担当の外のコード・道具・手順）：<無ければ なし>
覚えること（SOP・記憶に入れる学び）：<無ければ なし>
```
