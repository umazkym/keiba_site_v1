# 自動化ジョブ連携とデータ収集仕様書

本ドキュメントは、プロジェクト「KeibaAI_v2」において日々稼働している自動連携ジョブ（GitHub Actions）の全体像、および中核となるデータ収集（スクレイピング）とキャッシュ最適化の仕組みを、第三者が明確に理解できるように整理したものです。

## 1. 自動化ジョブの全体像（GitHub Actions）

本システムは、日々の競馬開催に合わせて「データ収集」「AI予測」「SNS発信」「ブログ記事生成」をリレー形式で完全自動実行できるよう、複数のジョブが連携して稼働しています。これらの処理はすべて GitHub Actions 上で実行されます。時間はすべて **日本時間 (JST)** です。

### 1.1 パイプライン（データ収集・予測・結果）

| ジョブ名 | ファイル名 | スケジュール | 概要と役割 |
| :--- | :--- | :--- | :--- |
| **Data Fetch (Morning Today)** | `keiba-data-fetch-morning-today.yml` | 金土日 **06:30** | **「今日のレース」**に対する最終的なAI予測を生成。当日の馬体重や出走取消などの直前情報を反映するため、朝に実行。 |
| **Data Fetch (Afternoon)** | `keiba-data-fetch-afternoon.yml` | 毎日 **13:30** | **「明日のレース」**に対する前日時点のAI予測を生成。出走馬が確定する昼過ぎ〜夕方の時間帯に合わせて実行。 |
| **Pipeline Runner (Results)** | `keiba-pipeline-runner.yml` | 毎日 **05:00** | **「昨日のレース結果」**を取得・パースし、DBに書き込む。この蓄積データが、次回のAI予測の精度向上（過去データ）に直結する。 |
| **Data Fetch (Morning)** | `keiba-data-fetch-morning.yml` | 手動実行専用 | 旧仕様のデバッグ・再実行用。任意の日付(`target_date`)を指定して、過去や未来の予測を手動で生成したい場合に使用。 |

## 2. データ収集（スクレイピング）の詳細仕様

`Data Fetch` パイプラインが日々ネット競馬からスクレイピングしているデータの **「収集範囲と判断ロジック」** について解説します。

### 2.1 対象レースと収集範囲
- **対象レース**: `target_date`（当日または翌日）に開催される、中央（JRA）および地方（NAR）のすべてのレースが出馬表取得の対象となります（ただし地方の「ばんえい競馬」など一部の非対応競技は除外）。
- **対象馬（Horse）**: 出馬表に記載されている**「当日走る全頭（通常1日あたり約500〜700頭前後）」**が、過去成績取得の対象となります。システム全体に存在する何万頭もの馬を無差別に取得しているわけではありません。

### 2.2 真のボトルネックと過去の課題
出馬表（約50レース）の取得は数秒で終わりますが、「当日走る600頭」の馬の過去成績ページをそれぞれ取得すると、ネット競馬のアクセス制限（IP BAN）を防ぐため1頭あたり最低2.5〜5秒の待機時間がかかり、**合計で1時間半（80〜90分）以上**の処理時間を要していました。これが「GitHub Actionsが90分タイムアウトで強制終了される」最大の原因でした。

## 3. 「DB主導」の究極のキャッシュ＆スキップ最適化戦略

上記の問題を解決するため、現在は非常に高度なバルクスキップロジック（`db_handler.py` -> `_build_horses_to_skip`）を実装しています。

### 3.1 概要：「ファイル」から「DB」へのキャッシュパラダイムシフト
以前は、取得に時間がかかるHTMLファイルをローカルに保存し（ファイルキャッシュ）、GitHubの `actions/cache` を使って使い回そうとしていました。
しかし、GitHub Actionsは「毎度空のコンテナで起動する」性質上、キャッシュが不安定で巨大化しやすく、タイムアウト時にキャッシュ保存自体が失われるという致命的弱点がありました。

これを抜本的に解決し、**「データベースそのものを『過去データの最強のキャッシュ』として扱う」**アーキテクチャへと設計を移行しました。

### 3.2 1クエリ・バルクスキップでの収集対象判定
パイプラインは、当日走る600頭を一つずつ判定するのではなく、処理の冒頭で**「巨大な1回のSQLクエリ」**を投げ、各馬の「過去成績の蓄積量（`valid_count`）」と「最終出走日（`last_race_date`）」を一括調査します。

ここで以下の **AND条件を満たした馬は、ネット競馬へのアクセス（取得）を一切行わず「完全スキップ」** します。

1. **`valid_count >= 5`（データが十分に存在する）**
   過去に5回以上走った記録が我々のDBに存在する馬。
2. **`last_race_date < 7日前`（最近走っていない）**
   最新の出走履歴が1週間以上前である馬。

#### なぜこの条件で100%安全にスキップできるのか？
- 馬の過去成績は、「新しくレースを走った時」以外に増えることはありません。
- すでにDBに5件以上の基盤データがあり、かつ1週間以上出走していないのであれば、**ネット競馬の馬のページにも私たちが知らない「新しい過去のレース結果」は1行も追加されていないことが数学的に証明できるから**です（Source of Truth をDB側に置く）。

### 3.3 スキップされず「収集される」条件（セーフティネット）
逆にフェッチ（収集対象）として抽出されるのは以下の馬のみです。

- **新規馬・データ不足馬（`valid_count < 5`）**:
  新馬戦に出走する馬や、システム稼働前から走っている未知の地方馬など。これらは必ず取得し、過去55走までの実績とマスターデータをDBに保管します。
- **最近走ったばかりの馬（7日以内）**:
  実は「毎朝の予測」と「毎深夜の結果反映（Results）」のパイプラインサイクルが正常であれば、数日前に走った結果もDBには入っているはずです。あえてこれを「再取得」するのは、**「深夜の結果収集ジョブがサーバーエラー等で死んでおり、昨日の結果を取りこぼしていた」という最悪のケースでも、このPredict前のfetchで自動的に自己修復・最新化（UPSERT）するため**の強力なシステムフェールセーフ機能です。

### 3.4 期待されるパフォーマンス（劇的な最適化）
この「データベース主導のバルクスキップ」により、1日あたり600〜700頭エントリーする馬のうち、**フェッチ（ネット取得）対象となるのは「新馬」や「短期間で連闘する馬」などの約100〜150頭へと激減**しました。

結果として、1時間半かかっていたパイプライン処理は**約15分前後**の圧倒的スピードで安全かつ余裕をもって完了する「強固なCloud Nativeアーキテクチャ」へと昇華しています。
