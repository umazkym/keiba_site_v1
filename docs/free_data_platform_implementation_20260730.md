# UMA-FREE 無料データプラットフォーム実装記録

更新日: 2026-07-30

## 目的

既に収集済みのレース、出走結果、競走馬、騎手、調教師、予測、払戻、対戦成績を再加工し、月額課金を前提にせず検索流入、再訪、当日レース閲覧を増やす。新しい外部スクレイピングは追加せず、既存データベースだけを読み取る。

## 実装範囲

- `/keiba-data`: 収録件数と馬・騎手・調教師・コース・AI成績への入口
- `/horses`, `/jockeys`, `/trainers`, `/courses`: 母数順のデータディレクトリ
- 個別詳細: 通算成績、競馬場、距離、馬場、人気帯、近走、出走予定、AI偏差値履歴
- コース詳細: 枠番、馬番、馬場、人気帯、脚質、騎手、調教師、払戻分布、最近の勝ち馬
- 重賞ハブ: 年度別結果とシリーズ集計
- レース詳細: 出走馬ごとの同条件馬・騎手・調教師成績を必要時だけ取得
- 横断検索: 記事、固定ページ、競走馬、騎手、調教師、コースを同じ検索結果へ統合
- マイデータ: お気に入りと閲覧履歴をブラウザ内に保存
- 馬比較: 2〜5頭を同じ指標で比較
- PWA: manifest、Service Worker、ブラウザ通知権限と動作確認
- SEO: データ専用XMLサイトマップ、公開ページのcanonical、母数によるindex判定、構造化データ
- 計測: `data_entity_view`, `data_search`, `data_favorite`, `horse_compare`

## データと性能の方針

DB全体を複製する集計テーブルは追加していない。今回の導入時点では、条件を限定したSQL集計、プロセス内TTLキャッシュ、FastAPIのCache-Control、Next.js ISRを組み合わせる。レース初期表示へ大きな集計を追加せず、条件別比較は展開時にだけ取得する。

データ専用サイトマップはバックエンドで`indexable_only=true`の対象だけを生成し、Next.js側で1日相当のstale配信を許可する。検索結果、マイデータ、比較画面はサイトマップへ含めない。

## 公開品質ゲート

1. APIの単体・回帰テストを通す。
2. `npx tsc --noEmit`、`npm run design:audit`、`npm run build`を順番に実行する。
3. 390pxと1440pxでデータハブ、個別詳細、比較、レース内条件比較を確認する。
4. 本番反映後にAPIの応答時間、Cloud Run CPU、Vercel転送量、404率を7日間確認する。
5. GSCでは`/horses/`, `/jockeys/data/`, `/trainers/`, `/courses/`をページ群別に分け、表示回数、CTR、平均順位、クロール済み未登録を週次確認する。
6. GA4ではデータハブから`data_entity_view`、保存・比較、出走予定、`race_view`へ進む割合を確認する。

## 2026-07-30 ローカル実測

ローカルSQLiteの95,936レース、448,796出走結果を対象に確認した。

- 集計サマリー: 222ms（キャッシュ済み）
- 馬名横断検索: 3,755ms（初回）
- 競走馬ディレクトリ24件: 2,845ms（初回）
- 東京芝1600mコース詳細: 552ms、2,513走
- レース条件比較: 63ms、8頭
- データサイトマップ: 9,981ms、6,187 URL、約497KB

一覧検索とサイトマップは初回集計が重いため、TTLキャッシュとCDN/ISRを前提にする。レース画面の初期表示では実行せず、条件比較を開いた場合だけ取得する。

## 反映順

1. Cloud Runへバックエンドを反映し、`/api/v1/data/summary`、コース詳細、競走馬詳細、レース条件比較、サイトマップを確認する。
2. その後にVercelへフロントエンドを反映する。順序を逆にすると、先に静的生成された一覧ページがAPI未提供の空状態をISR期限まで保持する可能性がある。
3. `https://uma-free.com/sitemap-data.xml`を開き、Search Consoleへ送信する。
4. 7日間はAPI p95、5xx、Cloud Run CPU、Vercel転送量、GSCクロール状況を確認する。

## Vercel静的生成タイムアウト対策

2026-07-30のVercelビルドでは、静的生成開始後に進捗が0件のまま60秒経過し、394ページがワーカー単位で3回再試行された。最終表示は`/sitemap-articles.xml`の失敗だったが、同時刻に全ページが再試行されており、個別XML生成ではなく、外部API待機を含む静的生成ワーカー全体の停止と判断した。

対策は次のとおり。

- 共通API fetchへビルド時8秒、通常実行時20秒の中断上限を追加
- ビルド時はコールドスタート再試行を行わず、空状態へ安全にフォールバック
- コース詳細19件と重賞詳細8件を全件事前生成からオンデマンドISRへ変更
- 約6,000 URLのデータサイトマップを動的Route Handlerへ変更し、CDNキャッシュを維持

通常API接続時は366ページを71.6秒で生成した。接続だけ受け付けて応答を返さないAPIを使った試験でも、8秒で各fetchを中断し、366ページを72.3秒で生成した。`staticPageGenerationTimeout`の延長には依存していない。

## 外部設定が必要な範囲

- コードの実装だけではPWAのインストール促進表示やWeb Pushのバックグラウンド配信を確定できない。現在の通知は利用者が権限を許可したブラウザでの動作確認までで、定期プッシュ配信は行わない。
- GA4のカスタムディメンション登録、Search Consoleへのサイトマップ送信、本番デプロイは管理画面またはユーザー操作が必要。
- 本番DBの変更、追加スクレイピング、広告配置の変更は今回の範囲に含めない。

## 収益評価

直接課金ではなく、検索流入増加、再訪、1セッション当たりの詳細閲覧、当日レース到達を先行指標にする。広告収益は既存配置のままページRPMと視認率で確認し、データページ追加と広告配置実験を同じ期間に重ねない。
