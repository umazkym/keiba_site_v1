# UMA-FREE 自動記事生成・公開システム 完全仕様書

**Document Version: 4.0 (Phase 1〜3 実装完了＋収益化改善パッチ適用版)**  
**対象リポジトリ: keiba_site_v1**

---

## 1. システム概要

### 目的
競馬情報サイト「UMA-FREE」向けに、データベースに蓄積された実レース結果から「独自計算による一次情報」を自動的に発掘し、SEOに適した記事を生成・品質確認・公開するまでの工程を自動化する。

### 設計の根本思想
インターネット上の既存競馬情報を再構築・再配信するだけのコンテンツは、Googleの「Helpful Content Update（HCU）」によりスパムや低価値コンテンツと判定されるリスクが極めて高い。
本システムは**「我々のDBでしか計算し得ない独自データ」を一次情報として生成**することで、この問題を根本から回避する。

具体的には「枠順×コース×期間の勝率・複勝率・単勝回収率」の実績値をDBから直接計算し、統計的に有意な「偏り（特異点）」が存在する有望なコースだけを自動探索して記事化する。ネット上の情報転載ではなく、自社DBの実績そのものが記事の根拠であり価値となる。

### 収益化設計思想（v4.0 追加）
PV数・広告収益に直結する以下の3つの構造的課題を解消する改善を本バージョンで組み込んだ。

1. **記事が「1コース×1記事」の単発構造で内部回遊が生まれない** → ハブ記事自動生成＋CTAブロック挿入で解消
2. **検索需要を考慮しない記事選定** → 競馬場別の検索需要重み付けで解消
3. **記事のマネタイズレイヤーが未設計** → OGP/構造化データ自動付与＋収益スコア記録で解消

### 全体フロー（ワンライン）
本システムは非同期かつ複数のエージェント（処理モジュール）が連鎖して稼働する設計となっている。

```text
DB（実レースデータ）
  → Python（特異点抽出・検索需要重み付け・記事プランニング）
  → TypeScript・LLM（ペルソナ執筆）
  → TypeScript・LLM（AIによる品質確認と自動修正のループ）
  → TypeScript（CTAブロック挿入・OGP付与・ハブ記事生成・Gitプッシュ）
  → Vercel（GitHubプッシュ検知による自動ビルド・公開）
```

### 稼働スケジュールとインフラコスト最適化
GitHub Actions の Cron スケジューラを使用して **毎日 08:00 JST** に自動実行を行う。
これにより、自前のローカルPCや常時起動サーバーを立ち上げることなく運用可能であり、ランニングコストは処理時に発生するわずかな Gemini API の従量課金のみ（月数百円以下、あるいは事実上の無料枠内）に抑制されている。

## 3. エージェント詳細仕様

### 【エンジン②】データサイエンティスト
有望なテーマを自発的に探し出すシステムの中枢・プランナー。

*   **ファイル:** `backend/scripts/agents/data_scientist.py`
*   **言語:** Python 3.11
*   **利用ライブラリ:** pandas, sqlalchemy, sqlite3

#### 役割
DBから「枠順バイアスの特異点」を統計手法を用いて抽出し、**検索需要重み付け**を適用したうえで被りがない記事指示書（`write_order.json`）を生成する。

#### 検索需要重み付け（施策B）

特異点スコアの算出に**競馬場別の検索ボリューム推定重み**を乗算し、東京・中山など検索需要の高い競馬場の記事を優先的に生成する。

```python
SEARCH_DEMAND_WEIGHT = {
    '中山': 1.4, '東京': 1.4, '阪神': 1.3, '京都': 1.3,
    '中京': 1.1, '新潟': 1.0, '小倉': 0.9, '函館': 0.85,
    '福島': 0.9, '札幌': 0.85
}

# スコア計算: 統計的偏差 × 検索需要重み
anomaly_score = (win_rate_std * 100 + roi_std * 10) * search_weight
```

本重みは Phase 6 の Google Search Console データ導入後に実データベースへ自動移行可能な設計。

#### テーマクラスター自動判定（施策A）

`theme_cluster` を `"asset"` 固定から、コースの開催時期と現在月を照合して自動判定する仕組みに拡張。

| テーマクラスター | 条件 | 状態 |
|---|---|---|
| `asset` | 通年のストック記事（デフォルト） | **実装済** |
| `seasonal` | 現在月が該当コースの主要開催月に合致 | **実装済** |
| `trend` | 直近30日の勝率変動が大きいコース | Phase 3.5 |
| `comparison` | 同一距離の2競馬場比較記事 | Phase 3.5 |

```python
VENUE_SEASONS = {
    '札幌': [6, 7, 8, 9], '函館': [6, 7, 8],
    '福島': [4, 7, 11], '新潟': [5, 8, 10],
    '東京': [2, 5, 6, 10, 11], '中山': [1, 3, 4, 9, 12],
    '中京': [1, 3, 7, 12], '京都': [1, 2, 5, 10, 11],
    '阪神': [3, 4, 6, 9, 12], '小倉': [2, 7, 8]
}
```

#### 処理フロー
1.  `posted_history.json` を読み込み、過去に記事化した投稿済みキーワードのSet（集合）を作成し重複リストとする。
2.  SQLクエリを発行し、DBから過去3年分の実レース結果・単勝払戻データを一括取得。
3.  DataFrame上で、コース×枠番ごとに勝率・複勝率・単勝回収率を一斉集計する。
4.  **フィルタリング（以下の全条件を満たすコースのみを有効とする）**
    *   1枠あたりの最低出走数が50件以上（少なすぎるサンプルのノイズ排除）
    *   全枠の平均単勝回収率が5%以上（払戻データの欠損コースを除外）
    *   最有利枠÷最不利枠の勝率比が **1.2倍以上**（戦略的価値・有意な偏りの存在確認）
    *   JRA主要10場のみ（マイナーすぎるローカル検索需要の除去）
5.  **特異点スコア**（勝率標準偏差×100 + 回収率標準偏差×10）に**検索需要重み**を乗算して降順に並び替え。
6.  上から順に重複リストと照合。投稿済みキーワードと重複しない「未開拓の最上位コース」を1件だけ選定する。
7.  **テーマクラスター**を自動判定し、詳細なオッズデータやレース概要を含めた `write_order.json` を出力。

#### SQLクエリ設計上の重要事項
*   NeonDB実データにあわせ、`race_returns.bet_type = 'tansho'` で単勝払戻をJOIN。
*   `race_returns.number_1` は **馬番** であるため、枠番ではなく `results.horse_number` とJOINして紐づける。
*   `course_type IN ('芝', 'ダ')` でDBの実値に合わせて障害レース等を除外。
*   出力時の `condition` 表示文字列生成にて `'ダ'` は `'ダート'` に可読性変換（例：「中山ダート1200m」形式）。

#### 出力スキーマ例（`write_order.json`）
```json
{
  "target_keyword": "中京芝1200m 枠順 データ",
  "theme_cluster": "seasonal",
  "reference_data": {
    "period": "2023年03月〜2025年12月",
    "condition": "中京芝1200m 良〜不良",
    "sample_size": 94,
    "key_metrics": [
      {"枠番": "1枠", "勝率": "5.0%", "複勝率": "21.3%", "単勝回収率": "0%"},
      {"枠番": "3枠", "勝率": "13.1%", "複勝率": "33.9%", "単勝回収率": "162%"}
    ],
...
```

### 【エンジン③】ペルソナ・ライター
事実に基づくプロの競馬記事を書き下ろす。

*   **ファイル:** `frontend/scripts/agents/agent_writer.ts`
*   **言語/モデル:** TypeScript / 役割別LLMルーティング
    *   構成ブリーフ: RPD 500の `gemini-3.5-flash-lite` を優先し、`gemini-3.1-flash-lite`、`gemini-3.5-flash` の順でフォールバックする。
    *   初稿生成: 品質順に `gemini-3.6-flash`、`gemini-3.5-flash`、`gemini-3.5-flash-lite`、`gemini-3.1-flash-lite` を試す。
    *   制限管理: モデルごとのRPM・TPM・RPDを `model_tiers.ts` と `gemini_quota.ts` で管理し、Actions側の日次上限も同じ値に揃える。

#### 役割
`write_order.json` の数値を読み解き、UMA-FREEの厳格なトーン定義書に準拠したMarkdownドラフトを生成する。

#### ライタープロンプトの主要制約ルール
*   **確認順序の提示:** 導入部の読者への「問いかけ・挨拶」は禁止。1文目から核心データを提示し、読者が最初に確認すべき材料を示す。
*   **事実ベース:** ポエトリーな文や「驚くべきことに」などの過度な脚色表現をせず、数字を出したら即座に因果関係の説明や分析に移る。
*   **結語の禁止:** 「まとめ」「総論」「今後の馬券戦略」的な見出しと文章は使わない。最後は「このコースの買い目ポイント」と `/races/today` への自然な導線で締める。
*   **構造制限:** 
    *   タイトル：30〜40文字で `[競馬場/条件] + [重要な数字] + [読者が取る判断]` 構成。
    *   ディスクリプション：120〜140文字。
    *   H2・H3見出しには必ず「数字」と「結論」を含めること。
    *   本文3,000字以上、データはリストではなくMarkdownのテーブルで描画。目安は3,400〜4,200字。
*   **内部リンク:** 本文中に手動の関連記事セクションや `[関連記事：ダミー]` プレースホルダーは書かない。関連記事はページ側で自動表示し、本文末には `/races/today` への導線だけを置く。

### 【エンジン④】編集長（エディター）
品質を担保するセルフリフレクションループ。

*   **ファイル:** `frontend/scripts/agents/agent_editor.ts`
*   **言語/モデル:** TypeScript / 役割別LLMルーティング
    *   複数観点レビュー: `gemini-3.5-flash-lite` を主力に、「検索意図」「本文深掘り」「トーン・事実性」の3観点を添削する。
    *   最終編集判断: `gemini-3.6-flash` を優先し、初稿と同じ品質順で下位モデルへフォールバックする。

#### 役割
ライターが生成した記事（`queue/pending/`）に対し、「機械的チェック」「Gemmaによる複数観点レビュー」「AIによる意図チェック・JSONパッチ修正」の3段階をかけ、全条件をクリアした記事のみを `queue/approved/` に昇格する。

#### 処理フロー（最大3リトライループ）
```text
for attempt in 1..3:
  1. seo_checker.ts で機械チェックを実行 → ミスがあればエラーリストを文字列化。
  2. [現在の記事本文] + [seo_checkerからのエラーリスト] を含めてGemini APIへ「修正指示」を要求。
  3. 【JSON差分パッチ】 AIは記事の全文リライトを行わず、以下形式で「差分パッチ」のみを出力する。
     {
       "status": "APPROVED" または "REJECTED",
       "fixed_frontmatter": { "title": "修正タイトル", "description": "修正デスク" },
       "content_replacements": [
         { "original": "置換前テキスト", "fixed": "修正後テキスト" }
       ]
     }
  4. TypeScript側でJSONパッチを原文に対して適用（置換を実行）。
     ・※表やリストを破壊しようとする要求があった場合は、プログラムロジックで安全のためにブロックする。
  5. パッチ適用後の記事に再度 seo_checker.ts を実行し、完全クリーンか確認。
  6. seo_checker完全PASS ＋ AI statusが「APPROVED」の場合 → ループ通過、大成功。
  
3回ループしてもREJECTの場合 → 未解決状態として `_revised.md` という名称で pending 内に放置（人間による手動確認キューへ回る）。
```

#### 収益ポテンシャルスコアの初期記録（施策G）
APPROVED時に `posted_history.json` へ追記する際、以下の収益関連フィールドを初期値 `null` で記録する。

```json
{
  "estimated_monthly_searches": null,
  "actual_pv_30d": null,
  "ad_revenue_30d": null,
  "rewrite_score": null
}
```

これらは Phase 4（GA4連携）・Phase 6（GSC連携）で自動入力ロジックが追加される土台となる。

#### JSON差分パッチ方式を導入した理由と背景
当初は「修正済みMarkdown全文」をAIに出力させていたが、Gemini Flashモデルの性質上、長い入力に対して細かい修正を依頼すると、指示していないテーブル（表）の消失や、本文の過度な要約・欠落が頻発した。
「AIには修正箇所だけ（検索文字列と置換文字列）を出力させ、プログラム側で文字列置換として適用する」方式に変更したことで、以下のブレークスルーが起きた。
*   AIの誤ったテキスト操作によるMarkdown構造（表）の破壊を100%防止。
*   APIへの出力トークンが本文全文分から「数百文字分のJSON」に激減し、処理速度とコスト効率が飛躍的に向上。
*   正規化ロジック（`\r\n` と `\n` の吸収など）や、置換に失敗しても既存の文章をそのまま維持するフォールバック設計により運用が強固になった。

#### SEOチェッカー（`seo_checker.ts`）の厳格な検証ルール
| チェック項目 | 条件 |
|---|---|
| タイトル / デスク文字数 | Title: 30〜36文字 / Desc: 120〜140文字 |
| タイトルに数字 | 必須 |
| 本文文字数 | 3,000字以上（改行・空白除く、`ARTICLE_MIN_BODY_CHARS`で調整可能） |
| 構造チェック | テーブルまたはリストが1つ以上 / H2が1つ以上 / H2はすべて数字入り |
| 禁止構造とNGワード | H2「まとめ」禁止 / 導入定型文や「いかがでしたか」等のAI特有の手癖フレーズ（数十語のNG辞書）を含むことを禁止 |
| 末尾終了パターン | 「鍵となる」「戦略に組み込む」「回収率向上に繋がる」などの**読者への能動的な指示・総論とみなされるフレーズで記事が終わることを正規表現レベルで完全禁止。** |

### 【エンジン⑤】パブリッシャー
Gitへの反映と最終クリーンアップ＋収益化レイヤーの付与。

*   **ファイル:** `frontend/scripts/agents/agent_publisher.ts`
*   **言語:** TypeScript

#### 役割
`queue/approved/` に配置された完成原稿を取得・クリーンアップし、**CTAブロック挿入・OGP付与・ハブ記事生成**を行ったうえで、本番のデプロイ監視対象ディレクトリへ移動させ、履歴を更新しつつ自動で Git Push する。

#### 処理フロー
1.  `queue/approved/` にファイル群があるか確認し、最も古い待機済みファイルを1つ取得。
2.  `target_keyword` を解析し、API等の外部通話に頼らず内部の変換マップ（例：`福島 → fukushima`, `ダート → dirt`）を用いて英語スラグを高速に自己生成する。
3.  Frontmatter の `draft: true` を消去（または `false` へ）変更。
4.  **【OGP・構造化データ自動付与 - 施策F】** Frontmatter に以下のメタデータを自動追加する。
    *   `og_type`: `"article"`
    *   `og_title`: タイトルを転記
    *   `og_description`: ディスクリプションを転記
    *   `article_published_time`: 公開日時のISO文字列
    *   `og_image`: スラグベースのOGP画像URL
5.  **【旧プレースホルダー掃除 - 施策E】** 旧プロンプト由来の `[関連記事：〇〇]` プレースホルダーが混入した場合のみ除去またはハブ導線へ置換する。新規生成記事では本文中に関連記事を書かない。
6.  完成形を `frontend/content/articles/{日付}-{slug}.md` として書き出す。
7.  元ドラフトファイルを `approved/` から削除。
8.  `posted_history.json` の該当履歴エントリに `draft: false`, `published_at`, `slug`、および**収益ポテンシャルスコアの初期フィールド**（施策G）を書き込んで更新完了。
9.  **【ハブ記事自動生成 - 施策C】** 同一競馬場の公開済み記事が **3件以上** に達した場合、ハブ記事（まとめページ）を自動生成または既存ハブを上書き更新する。
    *   ハブ記事は `{venue}-gate-data-hub.md` として `content/articles/` に配置。
    *   Frontmatter に `article_type: "hub"` を付与。
    *   距離別一覧テーブル＋データの読み方ガイドで構成。
    *   記事数が増えるほどテーブルの行が増え、情報密度が自然に向上する設計。
10. `git add .`, `git commit -m "Auto-publish..."`, `git push origin main` を順次実行。

#### ハブ記事の設計意図
ハブ記事は「〇〇競馬場 枠順」のような**ビッグキーワードを間接的に狙う**ピラーコンテンツとして機能する。

*   **内部リンク構造の強化:** 個別記事の被リンクが増え、各記事のSEO評価が底上げされる。
*   **回遊率の向上:** ユーザーが1つの記事から同一競馬場の他の距離データへ遷移しやすくなり、セッションあたりのPVが増加する。
*   **自動成長:** 記事追加のたびにハブ記事が自動更新されるため、人手を介さずコンテンツが充実し続ける。

## 4. GitHub Actions ワークフロー設計

**ファイル:** `.github/workflows/keiba-article-pipeline.yml`

### ステップ構成と進行管理
```yaml
on:
  schedule:
    - cron: '0 23 * * *'   # 毎日 08:00 JST (UTCで前日23:00)
    - cron: '45 2 * * *'   # 毎日 11:45 JST
    - cron: '45 7 * * *'   # 毎日 16:45 JST
  workflow_dispatch:        # 手動トリガー
```

1.  **検索需要・レース更新記事生成 (Step 1A)**: `news_topic_planner.py` を実行。Tavilyは企画候補の発見にだけ使い、`race_update` / `course_venue` / `jockey_profile` / `beginner_guide` のWriteOrderを生成。WriterEvidenceは公式確認事項とUMA-FREE保有データだけで構成し、外部媒体のタイトル、URL、要約、推奨、コメントは渡さない。
2.  **重賞記事生成 (Step 1B)**: `news_topic_planner.py`を主系統として、JRA G1/JpnI=D-21、G2/JpnII=D-14、G3=D-10、需要のある地方重賞=D-9またはD-3から、同一`entity_key + season_year`のWriteOrderを生成する。旧`grade_race_writer.py`は既定OFFの互換経路とする。
3.  **データ生成 (Step 1C)**: Python の `data_scientist.py` を実行。有望データがあればJSON生成（検索需要重み付け適用済み）、なければ何も出力しない。
4.  **存在チェック (Step 2/3 の前段)**: `data/write_orders` 直下に新しい設定ファイルが生成されたかどうかをチェック。
5.  **生成と編集確認 (Step 2/3)**: `test_pipeline.ts` を実行し、Gemma構成ブリーフ、ライター、Gemma複数観点レビュー、エディターを連鎖的に動作。
6.  **承認チェック (Step 4 の前段)**: `queue/approved/` に新しく `.md` ファイルが存在するかを監視し、カウントを `GITHUB_OUTPUT` へ格納。
7.  **パブリッシュ (Step 4)**: `if: steps.check_approved.outputs.approved_count > 0` に合致した場合のみ `agent_publisher.ts` が実行され、CTA挿入→OGP付与→ハブ記事生成→Gitプッシュ→Vercelデプロイの連鎖が行われる。

### GSC週次監査・手動改稿

`.github/workflows/keiba-gsc-seo.yml`は毎週水曜09:15 JSTにSearch Consoleの確定済み28日データを前期間と比較し、公開中の自己canonical記事から改善候補を最大10件報告する。通常は監査だけで記事を変更しない。手動実行時はartifactに含まれる正確なslugを1件指定し、既存ファイルのtitle、description、keywords、導入文、H2文言だけを改稿できる。数値、表、本文、リンク、canonical、公開日、entity、重賞更新段階、広告・レース導線は差分ガードで固定する。重賞カレンダー主導の新規生成と同年度更新はGSCより常に優先し、開催21日前から開催後3日の重賞を通常改稿から除外する。

### 重賞GSC日次監視・限定自動補修

09:15 JSTの独立workflowは確定済みGSCの表示80%減、順位30位悪化、複数URL、誤段階を読み取り専用で報告する。16:45 JSTの記事workflowは同じ判定を再実行し、D-21〜D0または結果確定済みD+1〜D+3の代表URLが一意の場合だけ`grade_race_search_repair`を最大1件作る。48時間クールダウンを適用し、title、description、keywords、導入文、既存H2だけを補修する。新規URL、本文事実、表、数値、リンク、canonical、entity、開催日、`update_stage`は変更しない。

### ニュース起点記事生成の仕様

`news_topic_planner.py` は、LangGraph風の固定ノード列として以下の状態遷移を持つ。

```text
BuildQueries
  → FetchTavily
  → FilterSources
  → ClusterTopics
  → BuildWriteOrders
  → PersistOrders
```

Tavily検索結果は外部記事本文の再配信に使わず、`allowed_claims` と `key_metrics` に分解してWriteOrderへ保存する。記事本文では外部リンクを出さず、ニュースで確認された材料を「出馬表で何を見るか」「馬場・枠順・脚質・AI予想のどこを確認するか」へ変換する。複数ソースから得た話題は `topic_bridge` で1つの確認順に束ね、外部ニュースを話題の入口、UMA-FREE内部データを数値根拠として分けて扱う。

検索流入最大化のため、ニュースPlannerは直近21日以内から開催後3日以内の重賞を優先してTavilyクエリを作る。対象は中央重賞だけでなく、帝王賞、さきたま杯、関東オークス、JBC、東京大賞典などの地方・交流重賞も含める。同じ重賞は新URLへ分割せず、`field_building → race_week → draw_confirmed → final_48h → race_morning → post_race`の順で代表URLを更新する。keywordsも確認済み段階に連動し、馬番・枠番がない段階の`枠順`、予測データがない段階の`AI予想`、確定着順がない段階の`結果`を使用しない。検索意図を別URLで広げる場合は、開催場単位のコース解説など恒常的に別意図のコンテンツを優先する。

重複防止のため、`posted_history.json`、既存Markdown、未消費WriteOrder、`data/news_topic_history.json` を参照する。既存記事や未消費WriteOrderと同じ `target_keyword` は必ず避ける。同一レースの記事は既定で1実行1本までに抑え、枠順・追い切り・馬場などの切り口は同一記事を育てる前提で扱う。必要な場合のみ `KEIBA_NEWS_MAX_TOPICS_PER_RACE_PER_RUN` で上限を調整する。直近2日分の `news_topic_history.json` は、同一topic_key・同一URLの再利用を避ける目的に限定する。ニュース候補は優先度を高めに設定し、`article:pipeline` 側ではニュース枠を1本予約して、通常のデータ記事にTavily起点記事が押し出されないようにする。

### セーフティネット（クオリティ・ゲートの仕様）
万一、どんなに特異点のあるレースを見つけたとしても、エディターが「NGワードが消えていない」「不適切な末尾になっている」と判定し3回リトライしてもREJECTだった場合、`approved/` ディレクトリにはファイルが供給されない。
この構造により、Step 4 の GitHubの Push処理が `if` 条件で安全にスキップされるため、**「少しでも品質ルールや仕様から外れたエラー記事は、人間すら介入することなく自動で破棄・放置される」という強力なスーパーバイザー監視構造**が担保されている。

EditorのJSON応答が崩れた場合や、AI Editorが非承認にした場合は、文字数・見出し・内部リンクなどの機械SEOチェックだけでは公開承認しない。Gemmaレビューは最終Editorへ渡す前に構造化メモへ圧縮し、レビュー本文のノイズで記事修正が乱れないようにする。Geminiの一時混雑（503/high demand等）は `ARTICLE_LLM_RETRY_ATTEMPTS` と `ARTICLE_LLM_RETRY_BASE_MS` に従って高性能・中性能モデルのみ短時間再試行し、クォータ上限時は再試行せず次モデルへフォールバックする。
