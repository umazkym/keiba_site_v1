## 1. システムの目的・思想

従来のLLMを用いた単純なスクレイピングまとめは、Googleの「Helpful Content Update」において評価されず、スパムとして扱われるリスクが高い。

本システムの目的は「データを右から左へ流すシステム」ではなく、**「当サイトにしか存在しない独自計算データを一次情報として生成・研磨する編集部の構築」** だ。ソースをまとめるのではなく、ソースから計算する。この一点がシステム全体の設計思想を貫く。

### 設計の鉄則（変更禁止）

| 鉄則 | 内容 | 違反した場合のリスク |
|---|---|---|
| 1エージェント＝1タスク | 情報収集・執筆・校正・分析を単一LLMに担わせない | コンテキスト崩壊・品質保証不能 |
| ナレッジとロジックの分離 | トーン定義・禁止ワードは外部仕様書で管理。LLMは処理のみ | 仕様変更のたびに全プロンプトを書き直す羽目になる |
| 物理的ストッパーの配置 | AIチェックに加え、TypeScript/Pythonによる機械検証を必須プロセスとする | AIの自己採点は信用できない。機械フィルタなしでは低品質記事がデプロイされる |

### エンジン① SEOプランナー兼戦略リサーチャー
**フェーズ**: Phase 3（未設計）  
**役割**: 「今、どのキーワードなら検索上位を取れるか」の戦略立案。  
**処理**: Search Console APIから「表示回数はあるが順位が11〜30位のクエリ」を抽出し、強化余地のある記事テーマを選定して `write_order.json` を出力する。

---

### エンジン② データサイエンティスト
**フェーズ**: Phase 2（設計確定、未実装）  
**役割**: ネットからの転載ではなく「当サイトにしかない独自計算データ」を生成するエンジン。これがシステム全体の品質の源泉であり、最優先で実装する。

**処理**:
- Pythonで競馬データ（netkeiba等）を取得・蓄積
- Pandas等で「過去N年間・特定条件下での枠番別回収率」「脚質×馬場×距離の複勝率」等の特異点を計算
- 計算結果を後述のスキーマに従った `write_order.json` として出力

**このエンジンがない間の代替運用**:  
`write_order.json` を手動で作成し、`agent_writer.ts` に渡す。Phase 1の現在はこの運用。

---

### エンジン③ ペルソナ・ライター
**フェーズ**: Phase 1（実装済み）  
**実装ファイル**: `frontend/scripts/agents/agent_writer.ts`  
**役割**: `write_order.json` を受け取り、Markdownドラフトを生成する。

**安全装置**:
- 起動時に `data/posted_history.json` を参照し、直近10件とのキーワード重複を確認。重複時は即時リジェクト（無限ループ防止）
- 水増し禁止：1,500字に届かない場合は記事を生成せず、理由を出力して終了

**保存先**: `agents/queue/pending/{YYYYMMDD_HHmmss}.md`

**⚠️ 未解決の設計課題**:  
`posted_history.json` への書き込みは現状エンジン③ではなくエンジン④（編集長）の `APPROVED` 判定後に行う設計だが、この書き込みロジックはPhase 1の実装に含まれていない。→ Phase 1補完タスクとして別途実装が必要（詳細は §4参照）

---

### エンジン④ 鬼の編集長兼SEOチェッカー
**フェーズ**: Phase 1（実装済み）  
**実装ファイル**: `frontend/scripts/agents/agent_editor.ts`, `seo_checker.ts`  
**役割**: ライターの原稿を「機械」と「AI」の二段階で検閲・修正する。

**処理フロー**:

```
ドラフト受信
  │
  ├─① 機械チェック (seo_checker.ts)
  │     文字数・H2数字・禁止ワード・リンクプレースホルダー等
  │     FAIL → 即リジェクト（AI検閲は走らせない。APIコスト節約）
  │
  ├─② AI検閲 (agent_editor.ts + EDITOR_SYSTEM_PROMPT)
  │     AI手癖・導入テンプレート・構造問題の検出と修正
  │
  └─③ 修正版の再機械チェック (seo_checker.ts を再実行)
        PASS → queue/approved/ に移動
        FAIL → _revised.md として pending に保存（要手動確認）
```

**設計上の重要ルール**:  
AIが修正した `revisedContent` は必ず `seo_checker.ts` を再実行する。AIは禁止ワードを別の禁止ワードに置換することがある。

---

### エンジン⑤ SEOパブリッシャー
**フェーズ**: Phase 3（未設計）  
**役割**: `queue/approved/` の記事を本番環境へデプロイし、内部リンク網を最適化する。  
**処理**: ベクトル検索で関連過去記事を特定し、`[関連記事：〇〇]` プレースホルダーを実際のリンクに置換してからGit Pushする。

---

### エンジン⑥ アナリスト兼スーパーバイザー
**フェーズ**: Phase 4（未設計）  
**役割**: デプロイ後のパフォーマンス監視とフィードバックループ形成。  
**処理**: GA4/Search Console APIからPV・CTR・直帰率を定期取得。「直帰率が高い記事」「古くなった記事」をエンジン①へ「リライト案件」として自動差し戻し。

## 4. Phase 1補完タスク（実装必須）

Phase 1の実装で意図的にスコープ外とした以下の処理を、Phase 2移行前に必ず実装する。

### タスク①: `posted_history.json` への書き込み

**対象ファイル**: `agent_editor.ts`  
**タイミング**: `finalStatus === 'APPROVED'` かつ `approved/` への移動完了後  
**書き込む内容**:

```typescript
type PostedArticle = {
  id: string;              // タイムスタンプベースのファイル名
  title: string;           // Frontmatterから取得
  target_keyword: string;  // Frontmatterから取得
  theme_cluster: string;   // Frontmatterから取得
  keywords: string[];      // Frontmatterから取得
  posted_at: string;       // ISO8601形式（draft: false に更新するタイミング）
  draft: boolean;          // approved移動時点ではtrue、パブリッシュ後にfalse
};
```

**実装箇所** (`agent_editor.ts` の APPROVED ブランチ内):

```typescript
// approved/ への移動が完了した後に追記
const historyPath = path.join(__dirname, '..', '..', '..', 'data', 'posted_history.json');
const history: PostedArticle[] = fs.existsSync(historyPath)
  ? JSON.parse(fs.readFileSync(historyPath, 'utf-8'))
  : [];

history.push({
  id: path.basename(filePath, '.md'),
  title: data.title || '',
  target_keyword: data.target_keyword || '',
  theme_cluster: data.theme_cluster || '',
  keywords: data.keywords || [],
  posted_at: new Date().toISOString(),
  draft: true,  // パブリッシュまではtrue
});

fs.writeFileSync(historyPath, JSON.stringify(history, null, 2), 'utf-8');
```

### タスク②: `_revised.md` の扱いポリシーの決定（★選択肢Bで仕様化・実装済み）

- **確定ポリシー**: `agent_editor.ts` の処理プロセス開始時に、該当ファイルの古い `_revised.md` が存在していれば自動的に削除（クリーンアップ）する。
- **理由**: 無人運用（GitHub Actionsの完全自動ループ）を前提とした場合、エラーの残骸が蓄積し、ストレージ容量の圧迫や不測のバグを引き起こすリスクを防ぐため、常にクリーンな状態で処理を開始させる。

## 5. エージェント間インターフェース仕様

Phase 2以降の実装でエンジン間の結合を正しく行うために、データの受け渡しフォーマットを以下に固定する。

### `write_order.json` スキーマ（エンジン②→③の契約）

```typescript
type WriteOrder = {
  target_keyword: string;       // 例: "中山ダート1200m 枠順 データ"
  theme_cluster:                // query_clusters.json のカテゴリに対応
    | "asset"                   // 長期資産型（コースデータ・血統解析）
    | "cycle"                   // サイクル型（重賞回顧・展望）
    | "explosive";              // 爆発型（荒れたレース直後の分析）
  reference_data: {
    period: string;             // 例: "2021〜2024年"
    condition: string;          // 例: "中山ダート1200m 良〜稍重"
    sample_size: number;        // 例: 312（母数の明記を強制）
    key_metrics: Record<string, string | number>[];  // テーブル化できる数値群
    source: string;             // 例: "netkeiba 集計データ"
  };
  competing_article_structure?: string[];  // 競合上位記事の見出し構成（差別化用）
  related_articles?: {
    title: string;
    slug: string;
  }[];                          // 内部リンク候補（プレースホルダー生成に使用）
};
```

**重要**: `reference_data.sample_size` は省略不可。母数のない数字は記事内でNGになる。

## 6. GitHub Actionsによる自動化機構（Phase 3で実装）

**⚠️ このセクションは Phase 3 の設計メモである。現時点では未実装。**

### 自動化ワークフローの設計

```yaml
# .github/workflows/auto_publish.yml（設計段階）
name: Auto Article Pipeline
on:
  schedule:
    - cron: '0 23 * * 1,3,5'  # 月水金 08:00 JST (UTC+9)
  workflow_dispatch:            # 手動実行も可能
```

### ワークフローのステップ設計

```
Step 1: データ収集（Python / エンジン②）
  └─ 出力: data/write_orders/{date}.json

Step 2: 記事生成（TypeScript / エンジン③）
  └─ 入力: data/write_orders/{date}.json
  └─ 出力: agents/queue/pending/{timestamp}.md

Step 3: 編集・検閲（TypeScript / エンジン④）
  └─ 入力: agents/queue/pending/{timestamp}.md
  └─ 出力（APPROVED時のみ）: agents/queue/approved/{timestamp}.md
                             data/posted_history.json への追記

Step 4: パブリッシュ（TypeScript / エンジン⑤）
  └─ 入力: agents/queue/approved/{timestamp}.md
  └─ 処理: [関連記事：〇〇]プレースホルダーを実リンクに置換
           公開ディレクトリへ配置
           posted_history.json の draft を false に更新
  └─ 出力: Git commit & push → Vercel自動デプロイ

Step 5: クリーンアップ
  └─ 処理: pending/ と approved/ の処理済みファイルを削除
```

### クオリティ・ゲートの動作

エンジン④がリジェクトした場合、`queue/approved/` に何も出力されない。  
Step 4はファイルの存在を確認してから実行するため、**低品質な記事はコミットされずActionsが正常終了する。**

アラート設計（Step 4実行なしで終了した場合）:
- Slack/Discord Webhook で「記事生成スキップ（品質チェック不合格）」を通知する
- 連続3日スキップが続いた場合は「ライタープロンプトまたはデータ品質の見直しが必要」として別アラートを出す
